# REVIEW.md

## Starter Code Review (`app/main.py`)

This document reviews the starter implementation, identifying specific defects across helper functions, models, database interactions, and endpoints, along with failing scenarios and resolutions.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` (lines 72-74) | Returns `{"status": "ok"}` unconditionally without verifying database connectivity. | Stopping MongoDB or passing an invalid connection string still yields `200 OK`. The contract requires `503 Service Unavailable` when MongoDB fails ping. | Added `client.admin.command("ping")` inside a try-except block, raising `HTTPException(503)` if ping fails. |
| 2 | `compute_late_minutes` (lines 33-38) | Directly replaced hour/minute on `punch_in` without timezone handling; used `minutes > 10` after integer division, incorrectly treating 09:40:01 as 0 late minutes; failed to truncate instants to whole seconds (R1, R2). | A punch-in at 09:40:01 for a 09:30 shift returned `0` instead of `10`. Naive/UTC datetime mixing caused incorrect calculations. | Converted timestamps to IST, truncated to whole seconds, created shift start in IST, and checked `(punch_in - start).total_seconds() > 600`. If true, returned `int(diff_seconds // 60)`, else `0`. |
| 3 | `compute_work_hours` (lines 40-41) | Used Python's built-in `round(..., 2)`, which applies banker's rounding (round-half-to-even) and float approximation errors. | `2.345` rounded to `2.34` instead of `2.35`. Violates business rules R4 and R8 requiring half-up rounding. | Implemented `round_half_up` helper using Python's `decimal.Decimal` with `ROUND_HALF_UP`. |
| 4 | `compute_overtime` (lines 44-48) | Counted overtime even for durations under 30 minutes; for overnight shifts, constructed shift end on the punch-in date instead of the next calendar day. | Punch-out 5 minutes after shift end returned 5 instead of 0 (violates R3 30-min minimum); overnight shifts had shift end off by 24 hours. | Added overnight shift detection (`shift_end <= shift_start` advances shift end by 1 day), and returned `floor(minutes)` only when `>= 30`, otherwise `0`. |
| 5 | `create_employee` (lines 77-85) | Check-then-insert race condition (`find_one` then `insert_one`); missing validation for `shift_start != shift_end`; no format regex for `emp_code`, email, and department; returned naive datetime instead of epoch ms. | Concurrent identical creations could cause race conditions; identical shift start and end passed; response body violated OpenAPI integer epoch ms format. | Added Pydantic schema validation (`EmployeeCreate` with regex and model validator for shifts), created unique index on `emp_code`, caught `DuplicateKeyError` to return 409, and serialized `created_at` as epoch ms. |
| 6 | `list_employees` (lines 89-96) | Used `skip = page * page_size`, which skips page 1 completely (e.g. page 1 skips 20 items); `total` counted the whole collection instead of matching the filter; lacked sorting by `emp_code` ascending. | Requesting `page=1` returned items from index 20 onward; filtering by department showed `total` equal to all employees across all departments. | Changed pagination offset to `skip = (page - 1) * page_size`, passed query filter to `count_documents(query)`, and added `.sort("emp_code", 1)`. |
| 7 | `punch_in` (lines 99-122) | Check-then-insert race condition; did not check if employee exists (raised 500 on `emp["shift_start"]`); leaked MongoDB `id` into response; failed to attribute overnight shifts to previous calendar day (R1); returned raw datetime instead of epoch ms. | Parallel punch-in requests created duplicates; invalid `emp_code` caused 500 error instead of 404; response violated schema by containing `id`; overnight early morning punch-in recorded wrong date. | Verified employee existence (404 if missing); applied R1 overnight shift date attribution; enforced compound unique index `(emp_code, date)` and caught `DuplicateKeyError` (409); removed `id`/`_id` and formatted response according to OpenAPI. |
| 8 | `list_attendance` (lines 124-151) | Fetched the entire matching collection into memory via `list(...)` and sorted in Python; leaked `id` attribute; did not validate `date_from > date_to`. | High memory usage and slow performance on 100k records; `date_from > date_to` returned 200 with empty list instead of 422. | Leveraged database index with `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`, added 422 validation for reversed date range, and formatted output according to contract. |
| 9 | Document Serialization / Legacy records | Failed to supply default values for legacy records that omit `half_day`, `history`, `late_minutes`, or `overtime_minutes` (per DATA_MODEL.md Sample 9). | Ingestion of legacy documents threw `KeyError` or returned incomplete response models. | Provided default fallbacks (`half_day: False`, `history: []`, `late_minutes: 0`, `overtime_minutes: 0`, `work_hours: None`) in `serialize_doc`. |
| 10 | MongoDB Client initialization (line 22) | `MongoClient` initialized without `tz_aware=True`, returning naive datetimes that cause timezone conversion errors. | Calling `.astimezone(IST)` on naive datetimes raised `ValueError` or used system local timezone instead of UTC. | Initialized `MongoClient(MONGO_URI, tz_aware=True)` and ensured all date/time boundary operations handle UTC and IST explicitly. |

---

### Non-Defects Examined

1. **Storage of dates and shift times as strings (`YYYY-MM-DD`, `HH:MM`)**:
   - Looked at whether dates and shift times should be stored as BSON datetimes.
   - **Conclusion**: Not a defect. `DATA_MODEL.md` explicitly specifies calendar dates and shift times as plain strings to prevent arbitrary timezone conversion and keep attendance calendar days unambiguous.

2. **Absence of User Authentication/Authorization**:
   - Looked at whether endpoints should validate JWT tokens or user roles for `regularized_by`.
   - **Conclusion**: Not a defect. The assignment specification explicitly states: *"free text, no authentication in this assignment"*.
